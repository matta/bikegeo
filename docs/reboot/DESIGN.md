# bikegeo Reboot: Design and Plan

A clean-slate reboot built beside the existing application under `cmd/bikegeo-reboot` and `internal/reboot/...`. This file describes the current design; git history holds past discussion.

## Working rules

- **Rolling-Wave workflow & prompt playbook:** see [WORKFLOW.md](WORKFLOW.md) for the full phase router ("what's next?"), Frontier vs. lower-tier model guidance, sub-slice splitting criteria, and copy-paste prompts.
- **Horizon rule:** `DESIGN.md` is the steering doc — requirements, cross-cutting invariants, confirmed domain rulings, and coarse intent per upcoming slice. Do not pre-specify implementation edge cases multiple slices ahead. Confirmed `Q#` architectural and domain rulings remain binding; implementation details already written for future slices (Milestones `12a`–`14`) remain preserved as **head-start guidelines** for when each slice reaches planning, which the slice planner refines against committed code.
- **Decision triage:** Matt decides **architectural, physical-model, and UX forks** (now if cross-slice; at slice planning if slice-local) and agents record his explicit rulings here. **Obvious implementation mechanics** (compiler-enforced caller updates, non-zero sentinels, routine `400` validation, internal file layout) don't need upfront rulings — the slice planner picks the clean default and notes it in one line in `SLICE<n>.md` for veto on review. Agreement between agents is not approval, and a plan is not permission to change code.
- **Living spec:** when a new ruling supersedes an earlier one, update the active rule in place (or leave a brief pointer) and let git history hold superseded prose.
- When a choice is open, sketch the options briefly and recommend one. Don't write a deep spec that assumes an answer. Number open questions `Q#` and never reuse a number.
- Prefer fewer types and clearer physical steps over heavier machinery. Show how a real bike assembly step reads in code.
- Back technical claims with arithmetic, existing behavior, or a measurement. Two agents agreeing does not prove an unmeasured claim.
- **Scoring words:** a build's **score** (0–100) is the weighted average of its 0–100 attribute scores (Q59, superseding Q35–Q37). Don't describe scoring as pricing or cost in prose; call each criterion's value its **attribute score** and the top builds **best-scoring**. `make boundary` bans the words `price`, `pricing`, `cost`, `cheap`, and `ledger` in reboot files (Q40).
- **Physical modeling improvements are in scope (Q72):** the focus redirect cut UI, surface, and infrastructure bloat (JS, MCP, trace UI, secondary pages, persistence, chart solver UI), not physical fidelity. Accurate physical modeling — such as head-tube bore / steerer / SHIS lower-cup compatibility and physical frame/seatpost/saddle geometry — is explicitly in scope for the reboot.

### Slice planning

Each slice plan is its own file, `SLICE<n>.md` beside this one (for example `SLICE11.md` or `SLICE12a.md`), and it lives only until Matt accepts the slice. Plan **one slice (or sub-slice) ahead** against actual committed code (Rolling-Wave; see [WORKFLOW.md](WORKFLOW.md)). Every new slice plan starts with a `Status: Planned <date>` line right below its title.

**Planning gate:** don't start planning a new slice while any `SLICE*.md` file remains beside this one, whatever its status (planned, partly implemented, blocked, or awaiting acceptance). The current slice must be implemented and accepted first. Instead of planning, list each remaining plan with its Status line and follow the state router in [WORKFLOW.md](WORKFLOW.md) to pick the next action (requesting review and acceptance once the slice is `Implemented`; see "After acceptance"). Hold to this even when Matt asks for a new plan. Planning resumes only when no `SLICE*.md` file remains.

Before writing a plan, get Matt's rulings on the slice's open choices (numbered `Q#`) and record them under **Confirmed decisions** here. The plan cites them and doesn't decide them.

Size the plan by the work. Count the code, test, template, and asset files the slice touches. The status edits to the slice plan and DESIGN.md don't count.

- **Small: one commit and no more than 3 files.** Keep the plan sparse: the goal, the rulings it rests on, the files and the change in each, the tests and their expected values, and the verification steps. The planning agent offers to implement it itself.
- **Anything larger.** Write the plan in enough detail that a less capable model (for example Sonnet) can implement it reliably without making design choices. It gives exact type, field, and function signatures; every caller to update; URL and form keys; the commit split with subjects; each test with its inputs, its expected values (measured by an independent probe), and their tolerances; the rules that bite; the verification steps; and an out-of-scope list. The planning agent suggests delegating the implementation to that model.

Each planned commit must pass `make pre-commit` on its own (`make check` doesn't run `deadcode`; Q144). Every plan's "Rules that bite" section ends by requiring the implementation handoff below.

#### Implementation handoff

The implementing agent's last step is to record what it did and the state it left. It does this whether it finished, stopped early, or got blocked. The record goes in the same change as the work, or stays uncommitted alongside the work if the work isn't committed. A reviewer adds its findings under the same section and doesn't rewrite the implementer's record.

1. **The slice plan's Status line** says one of: `Implemented <date>; awaiting Matt's acceptance`, `Partly implemented <date>; stopped after <plan step>`, or `Blocked <date> on <question>`.
2. **An `## Implementation handoff` section** sits right after the Status paragraph in the slice plan. It contains:
   - **Who and when:** the date and the model that did the work.
   - **Commits:** each planned commit's subject with its hash, or "not committed". For uncommitted work, list the files that hold it and which planned commit each change belongs to.
   - **Done and not done:** by the plan's step IDs (for example A1, W3, N4).
   - **Deviations:** every place where the code or tests differ from the plan, and why. Write "None" if there are none. A deviation needs a reason. "Seemed cleaner" isn't one; stop and ask instead (see the plan's header).
   - **Verification:** the result of `make pre-commit` on the final state, and the plan's live check: what you confirmed, with numbers, and where the screenshot is. If you skipped it, say so and why.
   - **Open issues:** findings, questions for Matt, and anything you noticed but left alone.
3. **DESIGN.md's Milestones line** for the slice uses the same status words as the Status line. Don't touch any other part of DESIGN.md. Only Matt's acceptance makes a slice "done" (see "After acceptance").

#### After acceptance

When Matt accepts a slice, delete its plan file in the same commit that marks the slice accepted. After that, the code, the tests, and git history are the record. That commit also does three things:

1. **The Milestones line** says `done and accepted <date>` and lists the slice's commit hashes in place of the plan link.
2. **Links to the plan:** remove or rewrite every link to the deleted file, in DESIGN.md and in other slice plans. A plan that builds on the slice names it by number and lists its commits.
3. **Anything that must outlive the plan** moves into DESIGN.md first. That means a ruling not yet under **Confirmed decisions**, or an open issue Matt wants kept. Acceptance closes the handoff's other open issues, and the rest of the plan is dropped.

## Requirements

- **(a) Readable physical code:** build structures from directional pose steps and component builders (seatpost, saddle, fork, spacers, stem, handlebar), not scattered trig. Code clarity replaces web trace introspection (Q48).
- **(b) Focused Web 1.0 interface (parity with legacy `compare`):** Go-rendered HTML/SVG with plain `GET` forms, URL query state, and zero JS (Q48, Q54), serving `/` (multi-frame comparison matrix) and `/bike` (single-bike inspector with schematic SVG; open separate browser tabs to compare builds visually). No Construction Trace UI, no side-by-side or overlayed views, and no legacy secondary pages (Q48, Q52).
- **(c) Validated Go catalogs + JSON agent/debug output:** compiled Go structs validated by the chart-consistency check in `catalog`'s `go test` (Q91, Q118), plus thin CLI JSON serialization of Go result structs for agents and debugging (Q49a). No MCP server, no file-based catalog persistence, and no chart-reconstruction solver UI (Q49, Q50).
- **(d) Fitting and `0–100` weighted scoring:** saddle fitting (height-first when rails clamp, Q60) and build fitting over the `docs/reboot/stems.yaml` stem catalog and part options (Q58, Q100), ranked by a 3-criterion fit gate and tunable `0–100` weighted attribute scores (Q59, Q59a).
- **(e) Multi-frame comparison:** rank all 19 catalog frames (or custom frame/size/fork/sag selections) by best achievable fit and score (Q50, Q52, Q56).

## Confirmed decisions

### Precedence over legacy specs

For reboot code (`cmd/bikegeo-reboot` and `internal/reboot/...`), this document takes precedence over conflicting legacy specifications in `AGENTS.md` (Architecture and Frame Datasets), `docs/WEB.md`, and `internal/ideal/readme.md`:

- `0–100` weighted attribute scoring (`Q59`, `Q59a`) supersedes legacy's unweighted `100 − Σ points lost` model.
- `docs/reboot/stems.yaml` (107 stems and composite `0–100` stem score, `Q58`) supersedes legacy's `mtb`/`gravel` stem catalogs.
- The 3-criterion fit gate (`R ≤ 1.0`, `|ΔY| ≤ 2.0 mm`, `|ΔX| ≤ 10.0 mm`), unified 4-tier ranking (`Q61`, `Q90`), and height-first rail clamping (`Q60`) supersede legacy's 2-criterion gate and Euclidean/rail-scan solvers.
- Direct `encoding/json` CLI output (`Q49a`) replaces legacy's shared `report.Document` Markdown CLI layer.
- Single-row `/` web compare without `+spec`/`-spec` query grammar or legacy secondary routes (`Q52`), defaulting to `redshift_shockstop_pro` (`Q62`) instead of legacy's hardcoded `0 mm` dropper.

### Go core, pure Web 1.0 server-rendered workbench

- Go owns the physical model, assembly, catalogs, comparison, and HTML/SVG rendering. Browser and CLI surfaces call it directly rather than duplicating geometry or scoring.
- Pure Web 1.0 (Q48, Q54): Go renders HTML and SVG directly from placements (`html/template`, embedded assets). Forms submit with plain `GET`, state lives in the URL query, and there is zero JavaScript (no bespoke JS, no vendored HTMX for now, no npm, no build step).
- `/` is the multi-frame comparison matrix and `/bike` is the single-bike inspector with three fixed server-rendered diagram views (`view=bike|seat|stem`) instead of free pan/zoom. Open separate browser tabs to compare builds visually.
- Thin CLI JSON output (`encoding/json` directly over internal Go result structs) serves as the agent-friendly and debug interface, with no duplicated Markdown CLI renderer or `report.Document` abstraction (Q49a).

### Pose-based assembly

- `Pose` is an immutable value. `Advance`, `Translate`, `Turn`, and `Face` return new poses, so branching from a shared attachment is safe. `Face(worldHeadingDeg)` sets an absolute world heading. It is used for parts leveled against the world, not against their mounting tube (saddle `RailPitchDeg`, handlebar `BarRollDeg`). (`pose.Trace`, `pose.Step`, `PoseSnapshot`, and unused `label` parameters on `Pose` methods are removed in Slice 11 per Q48.)
- Component functions (`PlaceStem`, `PlaceSeatpost`, `PlaceSaddle`, `PlaceHandlebar`, ...) return placements whose landmarks are `Pose`s. Each landmark's local axes have a documented physical meaning. For example, `BRP` and `SitBones` carry the rail frame, not a saddle-surface normal.
- Placement (moving along a construction path) is separate from outline projection. The renderer draws outlines in landmark frames without recomputing angles.
- Trig lives in `pose` (rule in AGENTS.md).

### `assembly` builds and measures; `web` only renders

Test: if fitting or comparison would need the code without HTTP, it belongs in `assembly` (or `compare`).

- Composition (frameset → seatpost → saddle, stem → handlebar) happens in one `assembly` entry point (`PlaceBike`).
- Any scalar derived from placed poses is a method on a placement type. Callers, including tests, call it rather than restating the expression.
- Outlines and readouts use the setup that was actually placed, never catalog defaults or a second computation.
- Catalog data is application input in `internal/reboot/catalog`. `assembly` never imports it.

### Frameset leveling: one recipe, two passes

`placeFramesetAtPitch(pitchDeg, frame, lowerCupMm, fork, wheels)` walks from `BB`: rear axle, then head tube top (reach, stack), then down the steerer by HTL, lower cup, and fork A2C, then rake at `+90°` to the front axle; separately, up the seat axis to `SeatTubeTop`.

1. Pass 1 (`PlaceUnpitchedFrameset`): run at 0° and measure `LevelingPitchDeg()`; on the basis fork and cup, the same pass gives the chart-consistency mismatches that catalog's `go test` holds to the chart's rounding budget (Q91, Q118).
2. Pass 2 (`PlaceFrameset`): run again rooted at `bb.Turn(LevelingPitchDeg())`. The axles come out level and every step uses real dimensions.

Rotating about `RearAxle` and re-centering `BB` equals rotating about `BB`, so no closed-form pitch trig is needed.

### Coordinate and sign conventions

| Area | Convention |
| --- | --- |
| World | 2D side view, `BB = (0,0)`, `+X` forward, `+Y` up, positive turns CCW. Lengths are `float64` mm; angles are `pose.Deg`, with the heading convention owned by `Pose`. |
| Wheels | Equal radii. Leveled axles sit at `Y = LeveledBbDropMm` (equal to `BbDrop` only at zero pitch); ground is at `Y = LeveledBbDropMm − R_wheel`. |
| Stem | From `SteererUp` (`180° − HTA`): `UpperStackMm` + `SpacersMm` + clamp/2 → `SteererClamp`; turn `−90° + StemAngleDeg`, advance `StemLengthMm` → `BarClamp`. (`UpperStackMm` is one `11 mm` constant and spacers are capped at `30 mm`, per Q82.) |
| Handlebar | `Face(−BarRollDeg)` from `BarClamp` (positive roll is clockwise); 3D grip offset projected to the side view → `HandGrip`. Backsweep is positive rearward; upsweep is positive upward. |
| Seatpost | From `SeatTubeTop` (seat collar, `180° − STA`): advance `TotalLengthMm − InsertionMm` (Q84; `InsertionMm` is shaft below the collar) along the seat axis, translate local `+Y` by `SetbackMm` → `RailCradle` (renamed from `SeatpostClamp` in Slice 12a per Q75a). |
| Saddle | `Face(RailPitchDeg)` (positive raises the nose); advance `−RailOffsetMm` (**positive moves the saddle rearward**) → `RailCenter`; `BRP` sits at `(+RailCenterToBrpMm, +RailToBrpHeightMm)` and `SitBones` at `(+RailCenterToSitBonesMm, +RailToBrpHeightMm + SitBonesElevationMm)` in the rail frame, where `SitBonesElevationMm` is height above BRP (not above the rails) (Q75a, Q75b). |
| Readouts | `BrpToGripDistMm = |HandGrip − BRP|`; `SitBonesToGripRiseMm = HandGrip.Y − SitBones.Y` (measured from the sit bones so it carries across saddles); `RearCenterMm = −RearAxle.X` (horizontal BB-to-rear-axle distance on the leveled bike, used for `RC / WB`). |
| Chart basis vs. installed fork | `catalog.Frame.BasisFork` (a `ForkSpec` with `SteererBasis`) and `BasisLowerCup` hold the chart's basis (Q120, Q121), keeping bare `FrameSetup` free of chart quirks. Installed forks pair with a physical `LowerCupSetup`. |

### Chart Basis Fork in the workbench

- `fork=basis` resolves A2C, cup, and sag (0%) from the frame's `BasisFork` and `BasisLowerCup` and the size's `ChartFrame`, in one place, and ignores submitted overrides. Those fields render `readonly`. Sag is also read-only for rigid forks.
- Only the cup + A2C sum moves the front axle, so locking loses nothing. On the Fenrir, a 12 mm EC44 cup + 483 mm A2C reproduces the basis 0 mm + 495 mm.
- This is a workbench rule only. `assembly` still accepts any explicit cup and fork.
- Every visible label says "Chart Basis Fork". The explanatory note is built from fixture data.

### Fitting (Q6–Q18, ruled 2026-11-19)

- **Q8, terminology:** the operation of finding a build's settings for a fit target is **Fitting** (noun and result type), **fit** (verb), and **`ApplyFitting`** (entry point). Don't call it "search" in code or docs.
- **Q7, saddle target:** the saddle fit target is **BRP**, the landmark the fit report measured. SitBones stays a model-derived readout.
- **Q6, solver policy for saddle fitting:** a direct solve is acceptable as long as forward assembly (PlaceBike) remains the final check of every fitted build. (Clamped rail fallback updated by Q60.)
- **Q9, rail range:** `PlaceSaddle` rejects rail offsets outside `±(RailLengthMm − ClampLengthMm)/2`, the same range fitting respects. This lands as its own commit after saddle fitting.
- **Q10, fixture rail and clamp lengths:** the Fenrir fixture's 60 mm rail length and 30 mm clamp length are measured and authoritative. A fitting that is limited by the ±15 mm rail range is a real finding, not a fixture artifact.
- **Q11, cockpit target:** the front-cockpit fit target is a **HandGrip** point in world X/Y (BB origin), like the BRP target. With the frameset fixed, the saddle and cockpit fits are independent.
- **Q12, solver policy for front-cockpit fitting:** M2 Slice 2 fits `SpacersMm` and stem `LengthMm` as continuous values with a direct 2×2 solve at the submitted stem angle and bar roll, reusing Slice 1's box logic. Discrete part options and preference penalties are M2 Slice 3. **Forward pose-based assembly stays the source of truth for geometry:** a direct solve reads each fitted input's direction from the probe placement's poses and never restates the assembly formulas, and PlaceBike checks every fitted build.
- **Q13, cockpit limits:** `StemSetup` carries `MaxSpacersMm` (the steerer allowance; `PlaceStem` rejects more, like Q9; fixed at `30 mm` per Q82) and `MinLengthMm`/`MaxLengthMm` (the stem range fitting may choose; `PlaceStem` ignores it).
- **Q14, one entry point:** `ApplyFitting` takes one `FitTarget` with optional BRP and HandGrip landmarks and returns one fitted build, so the workbench has one apply link.
- **Q15, saddle first:** saddle fit is the primary fit criterion and must be right. Cockpit fit is secondary. Build fitting never changes the saddle fit for a fixed fork; when a BRP target is set, every ranked build on that fork carries the saddle fitting's values.
- **Q16, solver policy for discrete part choice:** enumerate every part-option combination, place each one forward with PlaceBike, score it, and rank. No direct solve and no rounding of a continuous answer. (Stem catalog and scoring model superseded by Q58, Q59, Q59a.)
- **Q17, HandGrip miss penalty:** port the legacy oval ("Area of Reasonable Fit"): semi-axes 10 mm and 20 mm, major axis tilted 30° clockwise from vertical (world heading 60°), centered on the HandGrip target, free inside, 22 points per unit of normalized radius R beyond R = 1. (Scoring model superseded by Q59 and Q59a: 0–100 weighted scores with a light inside-oval slope.)
- **Q18, build ranking result:** a ranked list of the 5 best-scoring builds, each with its penalty lines and its own apply link. Slice 2's continuous fitting stays as the explanation (for example, "needs a 134 mm stem"). (Scoring model superseded by Q59, Q59a; renamed by Q100.)

### Handlebar choice (Q19–Q21, ruled 2026-11-19)

- **Q19, workbench first:** M2 Slice 4 adds a handlebar list to the fixture and a `bar` select to `/bike`. Continuous fitting and build fitting use the submitted bar unchanged. Bars join build fitting in a later slice.
- **Q20, bar list:** port all 15 bars of the legacy catalog (`internal/catalog/handlebars.go`) exactly, labelled as legacy catalog values with sources not recorded. SQlab bend starts are illustrative (legacy formula 55 + 0.9·rise).
- **Q21, roll:** `BarRollDeg` stays a submitted fixed input. Changing the bar keeps the submitted roll.

### Handlebars in build fitting (Q22–Q25, ruled 2026-11-19)

- **Q22, opt-in:** a `bar_options=selected|all` workbench control (renamed from `stock_bars` per Q101). `selected` (the default) keeps today's behavior: build fitting uses the submitted bar. `all` makes build fitting enumerate every catalog bar.
- **Q23, bar penalty:** bars are free. There is no bar band; bars compete only through the HandGrip oval and the stem and spacer bands. Bar preferences may become penalty bands later. (Superseded by Q30.)
- **Q24, roll locked:** every bar build fitting installs gets the submitted `bar_roll`. Roll enumeration is not planned.
- **Q25, result:** Q18 is unchanged: the 5 best-scoring builds across all bars, each row naming its bar. Several rows may share one bar.

### Seatposts, bar sweep, and fork choice (Q26–Q34, ruled 2026-11-19)

- **Q26, slice order:** Slice 6 is the seatpost select with setback notes, Slice 7 the bar sweep band, and Slice 8 fork choice in build fitting. Each has its own plan file.
- **Q27, the seatpost is fixed:** continuous fitting and build fitting never choose the seatpost or its setback. The workbench gets a `post` select of fixture seatposts. It replaces the free `post_setback` field: each post carries its setback, insertion limits (originally extension limits; revised by Q75a/Q84), and clamp length, and the page shows the setback read-only.
- **Q28, fixture seatposts:** generic posts with 0, 15, and 25 mm setback (illustrative, with today's Ritchey-based limits), and the Redshift ShockStop PRO at **12 mm setback when sagged** (owner-reported 2026-11-19; its `350/250/100 mm` insertion specs — with `250 mm` max insertion and clamp length illustrative — are defined in Q75c/Q84). The FAIR Drop Best is neither modeled nor offered.
- **Q29, setback notes:** with a BRP target, the saddle fitting block always reports the post setback that puts BRP on the target with the saddle centered on its rails. When saddle fitting stops at a limit, it also reports the setback that would reach the target with the rails held at the fitted offset. These notes are explanations. They are never applied or linked, and they keep the current post's insertion limits (revised from extension limits per Q84).
- **Q30, bar sweep band:** bars are scored by backsweep only. 16°–20° is free (every bar in that range scores the same), and each degree outside it is penalized 2 points. The line appears in every build ranking result, including `bar_options=selected`. This supersedes Q23's "bars are free". (Rate superseded by Q59/Q59a 0–100 weighted bar sweep score.)
- **Q31, fork set:** fork choice enumerates the fixture forks at their catalog A2C and default lower cup. Rigid forks run at 0% sag. Suspension forks run at 15, 20, and 25% sag. The CAD Baseline Fork is excluded.
- **Q32, fork and saddle penalties:** forks are free except for sag. A fork sag band is free at exactly 20% and penalizes 2 points per percent away from it, so 15% and 25% each lose 10 points. It applies to suspension forks only. A BRP miss line penalizes the saddle's remaining miss: free up to 1 mm, then 2 points per mm (illustrative). (Rates superseded by Q59/Q59a 0–100 weighted fork sag and BRP scores.)
- **Q33, fork control:** `fork_options=selected|all` (renamed from `stock_forks` per Q101), mirroring Q22. `selected` (the default) keeps the submitted fork. With `all`, each row names its fork and sag, and its Apply link sets them.
- **Q34, BRP miss always counts:** the BRP miss line scores the saddle fit itself, not the fork choice. It penalizes any failure to reach the BRP target, whatever the cause (frame, seatpost setback, fork, saddle). So it appears in every build ranking result that has a BRP target, including `fork_options=selected`. There, every row has the same miss: with the 0 mm post and the fit report BRP, every score drops by 77.2 points (78.7 → 1.5) and the ranking doesn't change. (Rate superseded by Q59/Q59a 0–100 weighted BRP scores.)

### Scoring words in code (Q35–Q40, ruled 2026-11-19)

- **Q35, band type:** the band type is `PenaltyBand{FreeMin, FreeMax, PointsPerUnitBelow, PointsPerUnitAbove}`, and the HandGrip oval's rate is `FitOval.PointsPerR`. The fields are rates (points per unit), so **penalty** keeps meaning an amount of points. (Superseded by Q59 0–100 weighted attribute scores.)
- **Q36, penalty lines:** each scored line of a build is a `Penalty{Band, PointsLost}`, held in `StockCandidate.Penalties` (since renamed to `ScoredBuild` in Slice 13d, Q100). The band-name type is `BandName`; its constants keep their `Band…` names and string values. Prose says "penalty lines". (Superseded by Q59 0–100 weighted attribute scores.)
- **Q37, score:** a build's 100 − points lost is its **score**: `StockCandidate.Score()` (now `ScoredBuild`), a **Score** column in the ranked-builds table, `data-build-cell="score"` (was `data-stock-cell`), and the note says "score = 100 − points lost". The best builds are "best-scoring". (Superseded by Q59 0–100 weighted attribute scores.)
- **Q38, free stays:** `FreeMin`/`FreeMax`, the "Free: …" preference note, and "free inside its range" keep the word *free*, meaning no penalty. (Superseded by Q59 0–100 weighted attribute scores.)
- **Q39, scope:** reboot code, tests, templates, and all of this file. Rulings are reworded without changing their substance. AGENTS.md's legacy Architecture bullet on scores stays as it is, because it documents legacy code that still uses those words.
- **Q40, enforcement:** `make boundary` bans the words `price`, `pricing`, `cost`, `cheap`, and `ledger` in the file names and contents of `cmd/bikegeo-reboot` and `internal/reboot`, like `chassis`. It matches in any case and inside longer words, so `prices`, `priced`, `PricedBand`, `CostPerR`, and `cheapest` are caught too. The list names whole words, not stems, so it reads plainly (revised 2026-11-19).

### Chart closure check (Q41–Q47, ruled 2026-11-19)

- **Q41, next slice:** M3 starts with a chart closure check for the Fenrir fixture chart (Slice 10).
- **Q42, M2 closed:** Milestone 2 is done and accepted. Roll enumeration stays not planned (Q24).
- **Q43, declared precision:** each `FrameChart` declares the rounding half-width of every published column the closure checks read, as a `ChartPrecision`, labelled in the fixture like other values. There is no inference code. The Fenrir uses ±0.5 mm for lengths and ±0.125° for HTA (a quarter-degree grid), marked illustrative.
- **Q44, fork and cup are hypotheses:** the CAD fork's A2C and rake and the CAD lower cup get no rounding terms. Only frame chart columns do: reach, stack, HTA, HTL, BB drop, chainstay, and wheelbase.
- **Q45, method:** port the legacy budget. Move each column by ± its half-width, rerun the unpitched frameset recipe forward (no closure equations restated), and take the larger change in the residual as that column's term. A check's rounding budget is the sum of its terms, and it passes when |residual| ≤ budget. There are no allowances or tiers. (Extended by Q57 for unpublished wheelbases and documented allowances.)
- **Q46:** superseded by Q47 (it put a budget table on `/bike`).
- **Q47, a data check, not a readout:** the closure budget validates fixture data and is not shown to users. `web.NewHandler` runs `assembly.CheckChartClosure` on the fixture chart once and panics if a check fails. The `/bike` "0° Closure Residuals" readout and `ChartBaseline.Residuals` are removed. (Revised by Q91: once `catalog` replaces the fixture in Slice 12c, closure runs in `catalog`'s `go test` only and the `web.NewHandler` startup panic is dropped.)

## Layout and boundaries

```text
cmd/bikegeo-reboot/       entrypoint; `serve` on port 8081 (and URL-query JSON CLI in Slices 13f–14a)
internal/reboot/pose/     poses, units, primitives
internal/reboot/assembly/ component setups, placements, fitting, scoring, chart consistency
internal/reboot/catalog/  19 frames, 22 forks, 15 bars, 4 seatposts, SQlab 610, default targets (stems.go in Slice 13b, weights in 13c)
internal/reboot/compare/  (Slice 13e) multi-frame expansion, fitting, ranking, pruning
internal/reboot/query/    (Slice 13f; /bike query in Slice 14a) shared url.Values query parsing for CLI and web (no HTTP/templates)
internal/reboot/web/      pure Web 1.0 handlers, HTML/SVG views, embedded templates (no JS)
```

- Dependencies flow `cmd → {web, query, compare, catalog, assembly}`, `web → {query, compare, catalog, assembly, pose}`, `query → {compare, catalog, assembly, pose}`, `compare → {assembly, pose}`, `catalog → {assembly, pose}`, `assembly → pose`. Neither `assembly` nor `compare` imports `catalog`; callers pass catalog slices as explicit arguments so both packages stay unit-testable with small fixtures. CLI subcommands call `query` and `compare`/`assembly` directly rather than depending on `web`.
- Add packages only when a slice needs them. Keep each component's setup and placement types with its assembly code; don't rebuild a catch-all `model` package.
- `make boundary` enforces the import isolation and the banned-term rule described in AGENTS.md.
- To reuse legacy code, read, audit, and port only what's needed. Never wrap an old implementation under a new name. Small duplicated primitives are acceptable; a shared package created just to avoid duplication is not. A parity test must explain differences, not assume the old result is right.

- **Q129, compatibility goes by fork class, not by A2C arithmetic (ruled 2026-11-22; Slices 16c and 16d; revises Q31):** this is how the bike industry describes compatibility. ## Milestone 5: Web UI Overhaul (future, post-cutover)

- **Slice 21, `/` compare UI redesign — Engineering Workbench pattern (captured 2026-11-21):** refactor `/` from a card-heavy SaaS layout into a zero-JavaScript, high-signal diagnostic workbench so parameter inputs and the top rows of analytical results share the initial desktop viewport without removing functionality, accessibility, or semantic structure. Pure Web 1.0 constraints stay (plain `GET` forms, URL query state, zero JS per Q48/Q54).
  - **Problems with the Slice 14b layout ("SaaS Card Bloat"):**
    1. *Excessive vertical consumption (above-the-fold starvation):* header, multi-row form controls, and summary card consume nearly 100% of a standard desktop viewport, pushing the ranked comparison table below the fold on every load and submit.
    2. *Container-in-container nesting:* outer form card wrapping nested `<fieldset>` cards (`Bikes to Compare`, `Rider Fit Targets`, `Cockpit & Seatpost`, `Ranking Limits`) plus a separate `Comparison Summary` card add visual noise and wasted vertical padding.
    3. *Redundant status surfaces:* the summary card echoes input values already visible in the form controls above it, burying genuinely new execution telemetry (configurations shown vs. total builds evaluated).
    4. *Always-visible reference prose:* multi-line explanatory paragraphs (coordinate conventions, sag caveats, blank/zero limit rules, and tier definitions) stay permanently expanded and push controls and results apart.
    5. *Disproportionate input widths:* short categorical selectors (such as the frame picker) stretch across the full container width, wasting horizontal real estate while forcing related parameters onto separate vertical rows.
  - **Engineering Workbench design principles:**
    1. *Unified control toolbar over nested cards:* replace nested cards and padded `<fieldset>` boxes with a single flat-bordered `<form>` container at the top of the workspace, arranging logical parameter groups side-by-side in a responsive multi-column CSS Grid (Scope, Coordinates, Components, Limits) separated by subtle vertical hairlines (`border-inline-end`), with compact control heights (`~2rem`) and tight vertical rhythm.
    2. *Progressive disclosure via native HTML (`<details>` / `<summary>`):* move static helper text, coordinate notes, model caveats, and ranking tier definitions out of the primary flow into native `<details>` drawers — a compact **Parameter & model notes** disclosure beneath the form action bar, and a single horizontal summary strip of colored tier badges (`Fits all`, `Fits BRP`, etc.) with an inline `Show tier definitions` toggle — reclaiming ~30% of vertical header height with zero JS.
    3. *Merged action & telemetry footer:* eliminate the standalone summary card; combine primary form actions (`Compare Bikes`, `Reset Defaults`) on the left of a subtle footer strip with concise execution telemetry (`Showing X of Y configurations · Z builds evaluated` and active target coordinates) on the right.
    4. *Inline metadata & scannable typography:* place units (`BB origin · mm`) in column group headers or field labels instead of repeating them in prose; apply monospace typography and `font-variant-numeric: tabular-nums` to numeric inputs and result cells for vertical scan alignment.
    5. *Data-first hierarchy:* place the primary results table immediately below the workbench toolbar with sticky headers, crisp row borders, and subtle hover highlighting; secondary diagnostic tables (leveled geometry and 12-attribute score breakdown) follow below, with exhaustive breakdowns collapsed inside native `<details>` disclosures by default.
